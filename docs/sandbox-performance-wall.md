# サンドボックスと性能の壁(2026-11-22 実測)

「AI ドリブン開発の裏側」の 5 枚目「サンドボックスの中身と、さばける量」に出した数字(k6 で 200 同時の失敗 4.73%、
SSH の新規接続 約 100/秒)が、**サンドボックスの性能で決まっていたのか、エミュレータの作りで決まっていたのか**を
測り直した記録です。

結論:

- **サンドボックスそのものは、コアを足すとそのまま伸びる。** 中継を通さずにパケットを送るだけなら、
  プロセス数に比例して 1 → 4 プロセスで 3.7 倍(2026-09-05 の測定では 3.9 倍)。
- **エミュレータの中継(BIG-IP の VirtualServerProxy、ALB の AlbListenerProxy)は、コアを足しても速くならない。**
  中継に 2 コアを渡すと、1 コアのときより処理量が約半分に落ちた。Python のスレッドは GIL(同時に 1 本しか
  Python のコードを動かせない仕組み)を取り合うので、コアが増えるほど取り合いの手間が増える。
- 200 同時になると、中継を通したときだけ p95 が約 1 秒に跳ねる(直接なら 4 ms)。このとき中継の CPU は
  1 コアの約 7 割で、使い切ってはいない。待ち受けの列(listen backlog)を 20 → 1024 に広げても変わらなかった。
  **1 秒の原因は、まだ特定できていない**(「CPU を使い切ったから」ではない)。

つまり「壁はサンドボックスでなく、エミュレータの中継の作り」は合っています。ただし以前の説明の
「1 コアの速さで決まる」は言い過ぎで、正しくは **「コアを増やしても中継は速くならない(かえって遅くなる)」** です。

## 2. HTTP: 中継あり・なし、中継に渡すコア数

`tools/perf/` の 3 本で測りました。毎回新しい TCP 接続で GET を 1 回、15 秒間。

- `relay_backends.py`: 後ろの Web サーバー 2 台(`engine/mock_http_server`、`python3 -m http.server` と同じ ThreadingHTTPServer)
- `relay_proxy_proc.py`: BIG-IP の中継(`engine.bigip_lb.VirtualServerProxy`、round-robin)だけを別プロセスで
- `relay_load.py <同時数> <秒> <測るプロセスの pid>`: 負荷をかけ、そのプロセスの CPU(100% = 1 コア)とコアごとの使用率を出す
  (`TARGET=ip:port` で宛先を変えられる。既定は中継)

負荷をかける側と Web サーバーは `taskset -c 2,3`、中継は `taskset -c 0`(1 コア)か `0,1`(2 コア)に固定。

| 条件 | 同時数 | 処理量 (req/s) | 失敗 | p95 | 測ったプロセスの CPU |
|---|---|---|---|---|---|
| 中継なし(Web サーバーへ直接) | 20 | 2,326 | 0.00% | 4 ms | Web サーバー 116% |
| | 50 | 2,259 | 0.04% | 4 ms | 116% |
| | 200 | 2,094 | 0.71% | 4 ms | 102% |
| 中継あり・中継に 1 コア | 20 | 2,339〜2,613 | 0.00% | 6 ms | 中継 67〜71% |
| | 50 | 2,308〜2,459 | 0.01% | 7 ms | 67〜71% |
| | 200 | 2,087〜2,279 | 0.07〜0.15% | **約 1,000 ms** | 68〜72% |
| 中継あり・中継に 2 コア | 20 | **1,417** | 0.00% | 18 ms | 中継 139% |
| | 50 | **1,308** | 0.00% | 21 ms | 130% |
| | 200 | **1,235** | 0.50% | 1,033 ms | 132% |
| 中継に 1 コア・待ち受けの列 1024 | 200 | 2,203 | 0.21% | 1,017 ms | 72% |

読み方:

- 中継なしと中継あり(1 コア)の処理量がほぼ同じ約 2,300 req/s なのは、**負荷をかける側(Python、2 コア)の上限**です。
  中継の上限ではありません。中継の本当の上限を見るには、k6 のような速い負荷ツールが要ります。
- 中継に 2 コアを渡すと、CPU は多く使う(139%)のに処理量は約半分になりました。GIL の取り合いです。
- 200 同時の p95 約 1 秒は、中継を通したときだけ出ます。TCP の再送待ち(1 秒)に近い値ですが、待ち受けの列を
  広げても消えず、中継の CPU にも余裕があるので、原因はまだ分かっていません。

## 3. 以前の数字との関係

| 以前の数字 | 測り方 | 今回分かったこと |
|---|---|---|
| 200 同時で失敗 4.73%・p95 約 4 秒(`docs/k6-load-testing.md`) | k6(Go、速い)→ ALB の中継(HTTP を読んでルールを選ぶ分、BIG-IP より重い) | 中継を通すと 200 同時で遅れが跳ねるのは今回も同じ。k6 は負荷側が速いので、今回より強く出た |
| SSH の新規接続 約 100/秒(`docs/unusual-verifications-gnmi-cps-automap.md`) | paramiko → BIG-IP の中継 → 実 SSH | 1 接続ごとに SSH の鍵交換(重い計算)が入るので、HTTP よりずっと少ない |

## 次の一手

- 中継を asyncio(1 本のスレッドで多くの接続をさばく)に作り替える。GIL の取り合いが無くなる。
- 200 同時の 1 秒の遅れの原因を、`ss -s`・`nstat`(SYN の取りこぼし、再送の回数)で突き止める。
- 中継の本当の上限を、k6 で負荷側の上限を外して測る(今回は k6 がこの環境に無かった)。
